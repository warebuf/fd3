Stack / StackPQ Design Notes
============================
Date: 2026-04-26

PROBLEM
-------
The StackPQ data structure was built around raw Effect primitives (Type + A/B/C params).
As the game design evolved, it became clear the stack needs to be card-centric, not effect-centric.
The StackPQ also lived outside GameState, creating two sources of truth and making
client sync (WebSocket) and censorship harder than it needed to be.

KEY INSIGHT
-----------
The stack's semantic unit is a card or card-effect, not a raw effect.
Effects (A/B/C params) should be the resolution instructions *inside* a stack entry, not the entry itself.

DECISIONS
---------
1. Move StackPQ inside GameState
   - GameState snapshots will include pending stack entries automatically
   - Censorship (hidden info) happens in one place before serializing for WebSocket send
   - No more two sources of truth

2. Create a StackEntry struct (card-centric)
   - Type: PlayedCard, TriggeredAbility, CounteredPermanent, etc.
   - CardID: which card this originates from
   - PopTime: when it resolves (real-time ms)
   - Hidden: for face-down traps etc.
   - Effects payload TBD / being redesigned from scratch

3. Redesign Effects from scratch
   - The old Effect struct (A/B/C ints) was a placeholder mental model
   - Will be rebuilt to fit the new card-centric stack

4. Don't add timing to the Card struct
   - Timing belongs to the StackEntry, not the card
   - One card can have multiple effects resolving at different times
   - Frontend gets timing from the stack entries, looks up card info via CardID

STACK DISPLAY RULES (frontend)
-------------------------------
- Card played -> shows in stack UI
- Card's triggered ability -> shows in stack UI
- Permanent ability -> lives on the card UI, NOT in stack UI
- Exception: if a permanent ability is being countered, it shows in stack UI

HIDDEN INFORMATION
------------------
- Some stack entries need to be censored per player (e.g. trap card: visible as
  "a trap is set" to opponent, but details hidden until triggered)
- Censorship is applied at serialization time before sending over WebSocket
- The engine always has the full uncensored stack

CHAIN MECHANIC (future work)
-----------------------------
- Game is more similar to Yu-Gi-Oh chains than MTG stack
- When a card/effect is activated, opponent gets a reaction window to respond
- Responses stack on top, resolve LIFO
- Chain sits open until both players pass or timeout
- PopTime + EffectIndex ordering in the current PQ already hints at this
- Reaction window / chain logic is long-term work, not blocking current refactor

IMMEDIATE NEXT STEPS
--------------------
1. Move StackPQ into GameState
2. Create StackEntry struct
3. Rebuild Effects from scratch
4. Reaction window / chain logic: later
